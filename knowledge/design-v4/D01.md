# D01 — Incomplete requests: editable event details / dados ausentes, a definir

Use for event sites, business pages, catalogs and profiles when the request names the product but omits editorial details. This is a DevKiller product policy, not a web standard. Preserve every supplied fact. Missing content is not a failed application.

Represent unavailable details as null. Render “To be defined” (English) or “A definir” (Portuguese). Keep code and interactions complete. Do not invent dates, venue addresses, prices, contact links or testimonial evidence. Fictional content is appropriate only if the request authorizes a demo, clearly labeled. Missing art can use an original local SVG, not a broken image or a pretend photograph.

Example initialization for a request that supplied only an event name:
```js
const initial = {name: suppliedName, description: null, venue: null, date: null};
const show = value => value?.trim() || 'To be defined';
// Load saved content first; initial is only for a successful null read.
const saved = await window.DevKillerDB.get('event-details');
const details = saved ?? initial;
```
Build an Edit details form for the missing fields. Keep submitted values as plain text, normalize empty optional values to null, and await DevKillerDB.set before confirming. Preserve the current UI values on write failure and offer retry. A read failure must not initialize or overwrite the database. Reuse the app's existing editing flow. The local editor is not a protected administrator account.

Do not coerce a missing price to zero or label it free. Do not construct a countdown without a valid date, a map without an address, or a mailto link without an email. Explain any dependent action with “Add the event date to enable reminders”, and link to Edit details. Other sections remain usable. An essential unknown business rule is a pending decision, never an invented rule.

Acceptance: supplied name is unchanged; unspecified venue displays a placeholder; editing and reloading retains the venue; failed storage does not report success; no invalid-date output. Model-proposed QA must not demand facts never supplied. Record pending content in summary/limitations without blocking preview. This guidance cannot turn broken code into a passing test.

Sources: user instruction dated 2026-09-14; DevKiller content-v1; modules/stacks.mjs database contract. Authored guidance, not a claim that every generated app has been tested.
