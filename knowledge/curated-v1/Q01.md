# Q01 — React state architecture: consistent filters, totals and persistence

Scope: react-v3. Reference checked 2026-09-16: https://react.dev/learn/choosing-the-state-structure . Original DevKiller synthesis, not a verbatim documentation export.

Keep canonical records once. Derive selected records, filtered lists and chart series from those records rather than maintaining independent copies. Represent mutually exclusive request states with one status field. Flatten relations with stable IDs. Update related values together.

Engine adaptation: separate src/data, src/lib, src/hooks and src/components. A persistence hook loads before enabling mutations and never seeds over a failed read. Keep draft form state separate from committed records. Compute the proposed next state from the latest committed state, await its write, then publish the state and success message. Block concurrent writes with a synchronous ref guard or queue; disabling a button alone is not an atomic lock. Read and write the exact same namespaced storage key. This storage guidance is Engine-specific, not a React API guarantee.

Acceptance: create a record, wait for confirmation, reload and navigate back; the same record appears. Simulated rejected storage writes retain the draft and display an error, with no success message. Changing a filter must update the list and any filtered totals consistently.
