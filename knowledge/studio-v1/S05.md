# S05 — Prevent and diagnose errors / QA seletor texto completo persistência concorrência

Use for every supported stack. Before returning code, trace one real user journey: action → state → storage/API → visible result. Check assumptions at each boundary. A syntax fix does not establish correct behavior; a passing startup test doesn't cover all actions.

Common prevention rules: imports must exist in the active profile; CSS classes must match markup; hidden/mobile-only controls need correct display rules; overlays must not intercept unrelated clicks; all inputs and icon buttons need names. Missing editorial data stays null with an honest placeholder, not a made-up requirement or fake zero.

Persist related changes consistently. Read before editing. A failed read must not reset a record. A failed write must show an error and preserve the user's work. Serialize writes with a synchronous ref guard or a queue: multiple handlers writing stale snapshots can lose favorites, object positions or form data. Keep undo history separate from saved state and do not write on every animation frame.

QA scenarios are independent, with fresh memory storage. text is exact innerText of the entire selected element. Bad: select a collection container and expect only one item title. Good: target that item's h3 or use count on filtered cards. Avoid expectations coupled to uppercase decoration, extra category labels or line breaks. For saved values, target the value element, not the entire definition list. Use existing supported actions, stable selectors and one concrete assertion at the end.

A failure report must name requirement, expected behavior and evidence. Distinguish actual functional defect, cosmetic issue, invalid test expectation and unavailable environment. Do not repeatedly repair good code to satisfy a flawed assertion. Preserve features and last working preview; never claim the model executed tests. No unbounded automatic retry or extra model call is implied by this guide.

Source: DevKiller scenario runner, persistence API and observed FORM/ROOMLAB evaluations, 2026-09-14. Development regression knowledge, not a benchmark score. Uses no client secrets or private document content.
