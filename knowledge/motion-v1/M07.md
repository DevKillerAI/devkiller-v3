# GSAP: timeline choreography, lifecycle and eligibility boundary
DevKiller curated research and implementation reference, 2026-09-23. This document teaches the library but does not enable it in generated apps.

## Current Engine constraint
GSAP is not installed/enabled for generated projects under the current policy recorded in M04. Do not emit `gsap` imports, CDN scripts or ScrollTrigger code. Do not silently add the dependency. If the user explicitly asks for GSAP, explain the current restriction and use the approved Motion/Anime.js capability unless the Engine's licensing gate has been formally changed. Keep these sequencing principles available for choosing an allowed implementation.

## When GSAP is a good fit after authorization
Use a timeline when a hero or short editorial sequence has intentional beats with overlaps, labels and a clear ending. Keep one timeline per scene; name labels by story beat; animate only the intended properties; do not make the user wait before reading or interacting. Use ScrollTrigger only for content whose narrative is genuinely tied to scroll, preserve normal scrolling, and provide a reduced-motion/non-scroll state.

## React lifecycle pattern after authorization
Use the official `useGSAP` integration or a scoped `gsap.context()` rooted at the component. Revert/kill animations and ScrollTriggers on unmount, route changes and breakpoint changes. Use `gsap.matchMedia()` for responsive choreography and cleanup. Avoid document-wide selectors, unmanaged global timelines, duplicate triggers after remount, and concurrent ownership of the same transform by GSAP and Motion.

## Validation
Test mount/unmount/remount, route navigation, resize across breakpoints, interrupted timelines, keyboard/touch access, reduced motion and scroll restoration. Confirm the final static state remains legible and controls work when animation is skipped. No output from this document overrides the licensing/availability gate in M04.
